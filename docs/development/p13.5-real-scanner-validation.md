# P13.5 Real Scanner Validation

## Purpose

P13.5 validates the real local workflow from an immutable published template to
its authoritative layout, printable PDF identity, live camera capture, offline
scanner result, and ordered multi-page completion. It replaces the fixture-only
entry point for this workflow without replacing the P10/P11 diagnostic screens.

This is an engine-validation UI. It is not the persistent production scan
session planned for P14.

## Published-template resolution

The template builder and Real Scanner Validation route share one
`TemplatePublicationService` in the running app. The selection screen lists
immutable versions from `TemplateRepository`; it never chooses "latest"
implicitly.

`PublishedScannerResolver` resolves the selected `TemplateId` and
`TemplateVersion`, then reconstructs its `LayoutDocument` through `LayoutEngine`
and `LayoutConfig.a4Default()`, the same authoritative path used by PDF export.
The resulting `TemplateDefinition` and exact ordered `PageLayout` objects form
the scanner context. No fixture layout or widget geometry is substituted.

P13 currently persists semantic published versions, not serialized layouts.
Historical reproducibility therefore depends on retaining the authoritative
layout configuration and engine behavior. Persisting a publication artifact
with its layout/config fingerprint is a future storage concern; P13.5 does not
introduce a second geometry source.

## Printed identity and wrong-page rejection

Every generated PDF page already contains the `TS1` QR payload:

`TemplateId + TemplateVersion + PageId`

The persistent final-scanner isolate decodes that QR from the owned high-quality
still before recognition. It compares all three values with the selected
`CameraScanContext`. A missing, malformed, wrong-template, wrong-version, or
wrong-page identity stops processing with a typed error. The UI does not assign
the result to the expected page silently.

Relevant failures include:

- `SCAN_PAGE_IDENTITY_NOT_FOUND`
- `SCAN_PAGE_IDENTITY_INVALID`
- `SCAN_TEMPLATE_ID_MISMATCH`
- `SCAN_TEMPLATE_VERSION_MISMATCH`
- `SCAN_PAGE_ID_MISMATCH`

## Camera, overlay, and coordinate mapping

The camera screen reuses the P10/P11 engine, analysis worker, readiness model,
single-flight coordinator, high-quality still capture, and persistent final
scanner worker. Preview remains independent from throttled analysis and final
recognition remains off the UI isolate.

The overlay consumes the four real registration points produced by the camera
analysis result. It performs no detection. A projective transform from the
`PageLayout` canonical registration points to those tracked points extrapolates
the true physical page corners. The source-frame page corners are then mapped
using sensor orientation, current device orientation, optional front-camera
mirroring, and the center-crop offset introduced by `BoxFit.cover`. Partial
tracking never fabricates a quadrilateral. There is no rule-of-thirds grid or
static document rectangle.

Overlay states and concise instructions are:

- searching: `Searching for sheet...`
- partial: `Keep all 4 markers visible`
- quality/stability failure: actionable guidance such as `Move closer` or
  `Hold steady`
- ready: `Ready to capture`
- capture: `Capturing...`
- scanner worker: `Processing page N of M`
- success: `Page N scanned`

Detailed metrics remain behind **Show diagnostics**.

## Auto capture and multi-page progression

The screen does not implement a second readiness system. Auto capture occurs
only when `CameraScannerCoordinator` receives the existing stable/ready signal.
The coordinator pauses analysis for the still, transfers owned encoded bytes,
resumes live analysis while the persistent worker scans, and prevents duplicate
or overlapping capture.

`ScannerValidationSession` is local, non-persistent P13.5 state. It owns the
selected template/version, ordered page IDs, current page index, and one result
per `PageId`. A successful page opens result review. Continue advances to the
next exact `PageLayout`, requires fresh readiness, and cannot accept the prior
page. Done is available only after the final ordered page.

## Result review

Review shows template name, version, page number, `PageId`, every question on
that page, the selected option label or decoded numeric value, and the explicit
`MARKED`, `BLANK`, `MULTIPLE`, `AMBIGUOUS`, or `INVALID` state. Ambiguity is not
converted into an answer. Bubble evidence and scanner timings remain in the
expandable diagnostics section.

## Performance notes

P13.5 preserves the P11.2 path: reduced grayscale analysis frames, one owned
accepted-frame copy, persistent ArUco analysis detector, high-quality encoded
still capture, transferable isolate bytes, and a persistent final scanner
worker. Page identity decoding adds one native QR decode per captured still,
not per preview frame. No PNG transport or UI-isolate recognition was added.

## Manual Android validation

Manual validation is required on a physical Android device:

1. Run `flutter devices`.
2. Run `flutter run -d <device-id>`.
3. Open the template builder, create a valid template, and publish version 1.
4. Generate and save its PDF; display it on another screen or print at actual
   size.
5. Open **Real Scanner Validation** and select that exact template/version.
6. Start the camera and point it at the generated page.
7. Verify the dynamic quadrilateral follows page movement, tilt, perspective,
   preview rotation, and center crop.
8. Verify searching/partial/hold-steady/ready states and automatic capture.
9. Verify recognized answers, including blank/multiple/ambiguous states.
10. For a multi-page template, scan every page in order and verify progress.
11. Present a different template, version, and page; verify each is rejected
    with the corresponding typed identity failure and can be retried.
12. Verify camera suspend/resume, reopen/dispose, smooth preview, and the
    high-quality still path.
13. Record capture, scanner-worker, and capture-to-result timing.

## Non-goals and P14 boundary

P13.5 does not add durable scan sessions, respondent/batch persistence,
duplicate detection, a review queue repository, analytics, authentication,
Firebase/Firestore, synchronization, or production dashboard integration.
Those remain P14 work. Marker IDs, layout density, page geometry, preprocessing,
measurement, and classification thresholds are unchanged.
