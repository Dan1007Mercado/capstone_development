# p14.4 ArUco packet identity

## Scope and rationale

p14.4 adds offline identity and duplicate protection to physical answer-sheet
packets. It keeps the existing ArUco registration and deterministic OMR
pipeline. QR, OCR, cloud lookup, and a second full-image detector are not used.

ArUco is retained because the scanner already performs one dictionary detection
pass. The detections are classified by role and then reused for alignment and
identity, minimizing added processing cost.

## Marker roles and reservation

The current dictionary is `DICT_4X4_50` (IDs 0 through 49).

- Registration IDs are allocated from 10 through 49 in groups of four. They
  remain stable per logical `PageLayout` and are the only markers used for
  correspondence and homography.
- Packet identity IDs are 0 through 9. They are never used as registration
  markers.

The dictionary does not have a safe 100+ range. Four ordered identity marker
slots therefore encode the decimal value `packetSequence * 10 + pageIndex`.
This supports 1,000 never-reused packet sequences and ten pages per packet.
The repository rejects generation beyond that explicit capacity rather than
wrapping. Codec version 1 is explicit in the protocol API; unsupported versions
return `PACKET_CODEC_VERSION_UNSUPPORTED`.

The four identity markers are 10 mm square with 2 mm gaps, centered in the
printable top header band. Geometry validation requires them to remain inside
the printable area, clear of registration markers, and outside question and
bubble regions. The PDF also prints `Packet <id>` and `Page x of y`. Those labels
are diagnostic only; normal scanning never OCRs them.

## Authoritative geometry

Packet rendering starts from the immutable `PublishedTemplateArtifact` and its
exact stored `LayoutDocument`. A derived `PdfRenderPlan` adds header markers and
labels while retaining the same `PageLayout`, bubble commands, question
regions, and four registration marker commands. No layout is rebuilt from
current defaults and the published artifact is not mutated.

The detector runs once. `MarkerRoleSplitter` separates the result into expected
registration markers, reserved packet identity markers, and unrelated markers.
Only registration markers participate in registration count, duplicate,
correspondence, and homography checks. The complete detection set is retained
on `PageAlignmentResult` for packet decoding and diagnostics.

After trustworthy alignment, `PacketIdentityResolver` projects identity marker
centers into canonical space, verifies the ordered header slots, decodes the
packet/page value, and resolves it in the offline packet catalog. It then checks
packet existence, template ID, template version, page ID, page index, total
pages, marker encoding, and the registration-selected `PageLayout`. Any
disagreement returns a typed error before a response can be claimed.

## Lifecycle and duplicate behavior

`PacketGenerationService` accepts only a published answer-sheet artifact. It
reserves monotonically increasing packet sequences, builds every physical page,
renders packet-specific PDFs, and stores packet metadata. Generation creates no
responses.

Packets begin `unused`. The first valid scanned page atomically:

1. validates decoded identity against the scan result;
2. creates one `ResponseId`;
3. permanently binds the packet to that response; and
4. stores the page result.

A multi-page packet becomes `partial` until every distinct page has arrived,
regardless of scan order, then becomes `complete`. A repeated
`packetId + pageId` returns the existing response with an explicit `duplicate`
status. It never overwrites the stored result or advances completion. Different
packets create independent responses; response slots are not preallocated.

## Persistence and atomicity

`PacketResponseRepository` defines sequence reservation, packet storage, query,
and atomic page claim operations. The in-memory implementation is deterministic
for tests and development. `FilePacketResponseRepository` serializes operations
and writes append-only, generation-numbered full-state snapshots through a
staging file and atomic rename. Readers load only the latest complete snapshot.
Consequently packet binding, response state, scanned pages, duplicate detection,
and non-reused sequence counters survive restart. A failed first-claim write
does not expose an orphan response or an unbound claimed packet.

## Failure handling

Typed failures cover invalid generation counts, exhausted codec capacity,
unsupported codec versions, missing/incomplete/extra identity markers, invalid
header geometry, unknown packet combinations, template/page mismatch, invalid
scan results, and storage failures. Identity failure does not weaken geometric
registration, while registration failure prevents packet claiming.

The scanner diagnostic result exposes decoded packet and physical page identity.
The development template screen provides packet count (default 25), generation,
packet/response totals, and packet metadata inspection. Product-grade workflow,
cloud synchronization, respondent identity, analytics, QR, and OCR remain
deferred.
