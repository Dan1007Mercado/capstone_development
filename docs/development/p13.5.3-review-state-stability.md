# P13.5.3 Review-State Stability

## Real-device failure

After a successful final scan, the Android validation screen could enter
`ScannerValidationSessionState.reviewing` and then repeatedly throw
`Null check operator used on a null value`. The review branch selected its
result with `_state.result!`, where `_state` was only the latest transient
`CameraScanState`.

Session state and coordinator state have different lifetimes. A completed
coordinator emission contains the `ScanResult` and advances the session to
`reviewing`, but camera analysis can keep publishing tracking state without a
result. The session remains in review while the latest coordinator result is
null, so the assertion was not a valid invariant.

## Durable review result

`ScannerValidationFlowController` now owns the successful review result
separately from the latest camera state. A `scanCompleted` event is consumed
only while the session is `scanning`. Recording success atomically moves the
session to `reviewing` and stores the same `ScanResult` for the review UI.

Tracking, camera, and failure emissions update diagnostics but do not clear or
replace the stored result. Repeated completion emissions while reviewing are
ignored, so `recordResult` runs once for that page. A rejected or duplicate
page never creates a review result.

Continue advances the session and clears the stored result before resetting
the coordinator for the next page. The final Continue also clears the result
when the session becomes complete.

If review is ever rendered without a stored result, the UI shows the typed
internal error `SCAN_REVIEW_RESULT_MISSING` instead of forcing a null value.
The result-bearing review path no longer reads `CameraScanState.result`.

## Async and disposal behavior

P13.5.2 behavior remains: live analysis resumes after still capture while the
single-flight final scanner worker runs. Auto capture remains disarmed during
that operation, and the coordinator suppresses camera-phase replacement after
`scanCompleted` or `scanFailed` until reset. The screen now adds its own durable
review boundary, so queued or future tracking states are harmless even if they
arrive after completion.

The coordinator subscription callback checks both `mounted` and the screen's
disposing flag. Disposal remains non-blocking on Flutter's UI path; stream and
runtime cancellation are started asynchronously, while callbacks are prevented
from calling `setState` once disposal begins.

## Memory-retention audit

The observed 15-39 MB large-object collections are consistent with temporary
full-page decode, canonical grayscale, normalization, and threshold buffers,
but do not by themselves establish a leak.

The ownership review found no full-page buffer retained by review state:

- `ScanResult` contains classifications and scalar/list diagnostics only; it
  has no canonical image, preprocessing image, `Mat`, or `Uint8List` field.
- `CameraScanState` contains camera diagnostics, timings, errors, and the small
  `ScanResult`; it does not retain captured JPEG bytes.
- captured bytes are local to one coordinator operation and are transferred to
  the worker with `TransferableTypedData`.
- `_WorkerScanResponse` returns only `ScanResult`, durations, and byte-count /
  checksum diagnostics, not source or canonical image buffers.
- the ArUco alignment session and temporary homography/warp Mats are disposed;
  the preprocessing backend disposes every temporary native Mat in `finally`.
- the persistent worker retains reusable detector/scanner infrastructure, not
  per-scan page images, and disposes its alignment backend on shutdown.

No major preprocessing rewrite was warranted in this phase. Android profiling
is still required to distinguish expected peak allocation and GC from unbounded
growth across repeated pages.

## Automated validation

The focused regression suite covers:

- completed result followed by repeated tracking states with null results
- retained result rendering during review
- repeated completion without double recording
- Continue clearing the review result and allowing the next page
- final-page review advancing to complete
- scan failure preserving an existing review result
- duplicate-page rejection creating no review result
- completed state without a result returning a typed failure
- reviewing without a stored result rendering
  `SCAN_REVIEW_RESULT_MISSING` without a widget exception
- lightweight source-contract checks that review/worker response models do not
  retain full image buffers

## Android validation status

Manual Android validation remains required. Repeat the exact capture-to-review
flow with camera tracking active, continue through every page, verify no stale
result appears, and observe memory/GC behavior for bounded reuse across scans.

## Identity architecture

Page-specific ArUco identity is unchanged. The selected immutable template and
version still supply all candidate `PageLayout` instances, marker IDs still
resolve the physical page, out-of-order scanning remains supported, and
completed pages remain blocked. QR and barcode identity were not reintroduced.
