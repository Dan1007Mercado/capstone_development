# P12 Dynamic Template Builder ExecPlan

## Goal

Provide an editable application-layer draft that produces a valid immutable
`TemplateDefinition`, previews the authoritative `LayoutDocument`, and renders
that exact layout through `PdfEngine`. Support all existing question types and
mixed types within or across sections without implementing publication.

## Existing State

The template domain already provides immutable definitions, typed IDs, five
question types, and `TemplateValidator`. `LayoutEngine` owns pagination and all
physical geometry. `PdfEngine` renders a supplied `LayoutDocument`. The debug
home already exposes engine validation screens.

## Architectural Constraints

- Builder state expresses semantics only; it never calculates bubble or marker
  coordinates.
- `TemplateValidator` remains the validation authority.
- `LayoutEngine` remains the only source of pagination and page geometry.
- `PdfEngine` consumes the same `LayoutDocument` returned for preview.
- IDs remain stable through label edits and reordering.
- Question type belongs to each question, not its section.
- P10/P11 camera, scanner, and recognition configuration remains unchanged.
- Published-template immutability and persistent drafts remain deferred to P13.

## Proposed Design

`TemplateBuilderController` owns the mutable editing session. Every outward
snapshot is a newly constructed immutable draft `TemplateDefinition`. Mutations
address sections, questions, and options by typed IDs. Monotonic draft-local
counters create IDs once; rebuilds, text edits, and reorders never regenerate
them.

Type switching preserves the `QuestionId`, prompt, required flag, and
description. It replaces incompatible configuration with the minimum valid
configuration for the target type:

- single/multiple choice: two editable options
- Likert: ordered 1-5 options, configurable to 1-7
- yes/no: authoritative boolean Yes/No options
- numeric grid: no options and a `NumericGridSpec`

`previewLayout` builds one definition, validates it, and passes it to
`LayoutEngine`. `generatePdf` uses a successful preview and passes its exact
definition and layout to `PdfEngine`; the returned artifact retains both inputs
beside the generated bytes.

The Flutter screen contains only editing controls and calls controller methods.
Its preview summarizes page count, section distribution, ordered question IDs,
and question types from `LayoutDocument`; it is not a WYSIWYG geometry editor.

## Tests

- Draft creation and immutable snapshots.
- Section/question/option add, remove, edit, and reorder behavior.
- Stable IDs through edits and reorder.
- 1-5 and 1-7 Likert semantics, yes/no, and numeric grids.
- Repeated type switching and incompatible-state removal.
- Mixed types within one section and across multiple sections.
- Validator failures returned as structured engine errors.
- Authoritative layout pagination and marker IDs.
- PDF bytes rendered from the same semantic/layout pipeline.
- Builder source remains free of physical coordinate construction.
- A builder-created page passes the real P6-P9 pure-Dart scanner stages after
  canonical alignment is injected.
- Widget state survives rebuilds and exposes validation/preview actions.

## Performance

P12 performs layout and PDF work only on explicit actions. Text edits and
reorders update small in-memory semantic lists. No camera or scanner hot path is
changed.

## Risks

- A type switch could retain incompatible options or a numeric spec.
- Reordering could regenerate IDs or alter content.
- Preview and PDF could accidentally use different layouts.
- Nested editor rebuilds could overwrite active text.

Tests cover each invariant. Text fields are keyed by stable semantic IDs, and
the controller remains the screen-lifetime source of truth.

## Completion Criteria

- All five semantic types are editable and freely mixable.
- Valid drafts pass `TemplateValidator`, `LayoutEngine`, and `PdfEngine`.
- Preview displays natural pagination from `LayoutEngine`.
- Builder-created geometry remains scanner compatible.
- No dependency, scanner threshold, camera, or publication changes occur.
- Repository format, analyze, and test gates pass.

## P13 Deferred Work

- Persistent draft storage and restoration across app launches.
- Publication workflow and immutable published versions.
- Revision creation and published-template identity lifecycle.
- Production file sharing/printing UX and final application navigation.
